# SpecLoop 产品案例：课程项目需求从争议到验收

## 案例边界

本案例使用仓库内可复现的合成课程项目讨论，结构来自常见小组项目场景，但不代表真实客户研究结论。它用于展示产品判断、Agent 工作流和验收设计；自动化指标来自仓库测试，模型 Token、成本和延迟必须由真实 API 调用产生。

## 1. 原始问题

团队需要在周五演示需求工具，但讨论中存在三类风险：

- 产品经理希望导入会议、群聊和反馈，开发认为首版只支持粘贴文本。
- 助教要求导出 GitHub Issue，开发认为只导出 PRD 即可。
- “所有内容暂存在浏览器本地”仍是未经验证的假设，删除和协作边界没有定义。

用户真正担心的不是缺少一份摘要，而是需求变更后无法解释“为什么这样决定”，导致实现、验收和历史依据脱节。

## 2. 产品目标与非目标

目标是把零散讨论转换为 `证据 -> 用户问题 -> 产品决策 -> 需求 -> 验收标准`，并让每个输出可回到原文。首版不做实时转写、协作权限或 Jira 双向同步，以便验证核心价值而不被平台工程稀释。

## 3. Agent 如何介入

1. Intake 将材料切成保留来源和行号的证据片段。
2. Reasoner 标记上传和导出的显式冲突，同时识别数据保留等缺失条件。
3. 问题按信息增益排序且最多 5 个，避免把所有不确定性都转嫁给用户。
4. 人类选择或改写答案后，状态机才允许生成需求和 Given/When/Then。
5. 模型输出只是一份提案，必须通过 JSON Schema、Zod、evidence ID 白名单和状态守卫。

关键 PM 判断是把“问得全面”改成“只问会改变实现或验收的事项”。问题上限是产品约束，也是 Agent 质量门。

## 4. 代表性决策

| 决策点 | 首版选择 | 依据 | 权衡 |
| --- | --- | --- | --- |
| 材料输入 | 首版缩小范围但保留可扩展上传入口 | 产品与开发对范围冲突 | 控制交付风险，不丢失后续需求 |
| 输出格式 | 支持 Issue-ready Markdown | 助教用它检查任务可执行性 | 增加导出实现，换取明确验收价值 |
| 澄清策略 | 高风险优先、最多 5 问、一次一问 | 组员反对一次抛出大量问题 | 牺牲覆盖数量，提升回答完成率 |
| 最终权限 | 人类接受或修改 | Agent 不能替代产品责任 | 增加审核步骤，降低错误承诺 |

## 5. 需求与验收示例

需求：每条需求和验收标准必须能沿追踪关系回溯到至少一个原始证据片段。

- Given：系统已生成需求包。
- When：用户打开任一需求或验收标准的来源。
- Then：系统展示对应原文、材料名称和行号。

这条标准避免使用“追踪清晰”之类不可测试表述，并把用户问题转成可观察行为。

## 6. 变更影响闭环

新反馈为“课程验收必须现场上传 PDF，不能只粘贴文本”。SpecLoop 不覆盖旧需求，而是：

1. 保存反馈原文为新证据。
2. 给相关输入决策和需求添加 `challenges` 关系。
3. 将相关节点标为 `at-risk`，不影响无关决策。
4. 要求人类确认旧结论仍有效或后续修改。

这使变更成为可审计事件，而不是文档最后版本中的静默覆盖。

## 7. 成效与证据

已验证：

- 11 个测试文件、33 项自动化测试覆盖完整工作流、模型边界和服务端限流。
- 演示数据的需求和验收标准来源覆盖率为 100%。
- 8 条合成冲突 smoke fixtures 的 binary precision / recall 为 100%，仅代表该小型集合。
- Provider usage、缓存 Token 计价、失败 telemetry 和未配置价格状态有回归测试。

尚未验证：

- 开放域讨论材料上的冲突识别准确率。
- 真实用户对澄清问题的直接接受率和修改率。
- 真实模型 P50/P95 延迟、平均成本和 fallback 率。

真实模型运行后，Evaluation 会直接展示上述 Token、成本和延迟数据，不使用预填示例冒充测量结果。

## 8. 下一轮验证计划

- 收集至少 20 份脱敏课程文档或公开 Issue 讨论，由两名标注者确认冲突、缺失条件和有效问题。
- 对比 Demo Reasoner 与真实模型的 precision/recall、question utility 和人工修改率。
- 分材料长度报告 Token、成本和 P50/P95 延迟，定位上下文压缩机会。
- 记录被模型拒绝或 fallback 的原因，区分网络、限流、schema 和证据引用错误。
